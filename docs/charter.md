# 项目约定

## 一句话

Axiom 是一个仓库、一套证据规范、四类按目标分层的模块。工具可以换，判定标准不换。

## 为什么合成一个项目

原来两边的材料各自都写得挺完整：一边是二进制逆向的本机链路，一边是产品与技术栈拆解的方法论；再有六模块工具链和一套"改动是否生效"的验证习惯散在别处。重复的不是脚本，是**判定标准**——同一个"命中算不算数"的问题，在几个地方各写了一遍，措辞还不一样。

合起来之后：

- 判定标准只有一份：`docs/evidence.md` + `docs/verification.md`。
- 工作流程只有一份：`core/workflow.md` + `core/routing.md`。
- 目标按类型分层，模块之间不互相 import，可以单独维护、单独淘汰。
- 新能力有固定入口（`targets/_template/`）和固定注册处（`core/routing.md`）。

## 四层怎么划的

按**目标是什么**划，不按工具划。工具会过时，目标类型不太会：

| 层 | 目标 | 证据的典型形态 |
| --- | --- | --- |
| native | PE / ELF / 原生二进制 / 固件 | 伪代码、指令、偏移、evidence_id |
| mobile | APK / AAR / 应用运行时 | 类与方法、资源引用、模拟器回显、UI 层级 |
| web | 站点 / 接口 / 前端 bundle | 原始请求响应、状态码、header、bundle 里的地址 |
| product | 产品 / 平台 / 技术栈 | 公开可观测行为、接口面、版本与依赖线索 |

## 什么不收

- 具体目标、厂商清单、真实域名与内网地址、样本、漏洞证据、凭据。
- 依赖特定机器绝对路径才能跑的脚本；路径一律走参数或环境变量。
- 只针对单一对象、换个目标就失效的技巧，除非能抽出通用部分。

## 版本与兼容

语义化版本从 `0.1.0` 起。改动规范文档（evidence / verification / routing）算 breaking change，要写进 CHANGELOG 并同步所有模块的引用。
