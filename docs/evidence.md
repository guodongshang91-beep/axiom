# 证据规范

全仓库共用这一份。模块 README 只引用，不复制。

## 结论三件套

每条结论写成三行，缺一行就不算结论：

```
结论：   <一句话，说清观察到了什么>
证据：   <伪代码 / 指令 / 偏移 / 原始响应 / 行号 / evidence_id>
局限：   <这个结论在什么条件下成立，什么情况下不成立>
```

反例："该接口存在未授权访问。" —— 没有响应体、没有对照、没有范围，无法复核。

## 三种状态，别混着写

| 标记 | 含义 | 能怎么用 |
| --- | --- | --- |
| observation | 直接观测到的原始材料 | 可作证据 |
| inference | 从观测推出来的解释 | 必须写推断依据，不能当结论用 |
| unknown | 没查 / 查不到 / 工具不支持 | 明写未知，不要留白让人猜 |

产品拆解那边的"事实 / 推断 / 置信度"和这里是同一件事，只是多一档置信度评级（🟢 低风险 / 🟡 需关注 / 🔴 高风险）。评级跟着证据走，不跟着印象走。

## 证据怎么固定

- **留原始材料**：响应头与响应体、命令完整回显、伪代码片段、文件哈希。摘要不能替代原件。
- **可复现**：写清命令、参数、时间、环境版本。别人照着能跑出同一份材料。
- **引用而非转述**：REA 类工具返回 `evidence_id`，案例里直接引用，不把内容手抄一遍。
- **对照实验**：任何"命中"都要有对照，见 [verification.md](verification.md)。

## 静态不等于执行

反编译器给出的是静态结果，不能写成"观测到该函数被调用"。静态推断写 `inference`，运行期观测才写 `observation`。这条在 native、mobile、web 三层都一样。

## 淘汰清单也要留

被判定为假阳性的命中，连同判定理由一起记下来。只留"成功"的案例，后来的人会把同样的坑再踩一遍。
